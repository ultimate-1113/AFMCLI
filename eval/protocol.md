# Paired evaluation protocol

Use Apple's installed on-device system route only when it reports AFM 3 Core Advanced. Use greedy decoding, a new session per generation and one active request. Compare the same task, document, constraints and output fields. Direct receives the textual output contract and runs one unguided model call. Verified adds native schema guidance where applicable, original-source or type checks, conditional retries, and the deterministic transaction executor for edit. The direct editing baseline receives the same trusted transaction and must return the final document. This compares complete application strategies and does not isolate the effect of each component.

Development uses 20 hand-authored Japanese and English cases. The held-out panel uses 54 different documents or instructions, six per task. Variants of a document stay in the same panel. Six groups have a meaning-preserving perturbation and an expected change. Summaries are scored against the requested segment IDs, ignoring return order. Extract fields require complete multisets. QA accepts one of the specified exact answers after NFC, case and whitespace normalization. Returned offsets are checked against the original UTF-8 bytes separately. Structure and edit require a type-sensitive full JSON match. For free writing the checks cover only listed content and form constraints. An unanswerable case may pass by abstaining. A held answer does not pass a solvable task. A transaction rejected for its stated precondition must preserve the whole document. For solve, require feasibility, chosen assignment, every objective value and the tie count; additionally score the natural-language interpretation against the intended coefficients, bounds, relations and priority order. Count both directions of change on paired cases. The first eight task panels were fixed before initial development. The solver extension added three development and six held-out items before the first solver run and before any held-out run.

Tune on development only. Record development policies that were actually tried and select before opening held-out or external outputs. Freeze Rust sources, fixtures, evaluator, dependency lock and this protocol with SHA-256 before the first held-out call. Use the same final executable for both evaluation panels. A change affecting the inference or scoring after seeing an evaluation set requires a disclosed new evaluation. Publish all observed outcomes including regressions, abstentions and inactive constraints. Sampling cannot establish universal optimality or exclude pretrained exposure to public data.

Independently select published examples by SHA-256 order of a fixed prefix and the source question ID. JSQuAD has 16 answerable examples from different articles. English SQuAD v2 has eight answerable and eight unanswerable examples, each from a different article. JNLI has five examples per original relation label, with distinct source image groups across the sample. Source files and exact hashes are pinned in external.py. Fixtures are materialized directly from the authors' data. Keep the external source text, model output and transcripts local; publish IDs, measurements and scores. These small stratified samples are probes and do not implement an official leaderboard score. QA additionally reports character-overlap F1 for Japanese or word/punctuation-overlap F1 for English.

The final policy uses a separate evidence-support reading for grounded QA by default. Also measure a fast condition without that second reading on every held-out and external QA job. Select defaults using development alone. The measured development series tested a named fallback for classification, independent boolean decisions per label, an answerability field, a second support reading, rewriting instructions at the instruction level, and ambiguity expressed by empty solver arrays.

Use an additional synthetic integration exercise for over-context material, contradictory windows, bounded repair and images. Report this separately from the held-out scores. The library's offline checks also test duplicate JSON keys, Unicode offsets, transactions, timeouts/model gate and error paths through the CLI.
