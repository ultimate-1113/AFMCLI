# 目的・残りタスク・直前の出力を引き継ぐ試験

日本語の変更通知を時系列で読み、最後に「いま有効な値」とその根拠となる原文IDを答えた。1区間ごとにオンデバイスのAFM 3 Core Advancedを新しい `fm respond` で呼ぶ。すべての方式が同じ目的・残りタスク・新着資料を受け取り、同じスキーマで短い状態メモと根拠IDを出す。違いは、次の段階で過去の何を読めるかにある。[事前条件](protocol.md)

| 方式 | 次の段階に渡す過去の情報 |
|---|---|
| 全履歴 | それまでに届いた全原文と各段階のメモ |
| 直前出力 | 前の段階が出したメモ（最大160文字）と原文ID（最大3件） |
| 原文再読 | 直前出力に加え、そこに含まれるIDから引き直した原文（最大3行・合計1,200バイト） |

原文IDを一つ添える採点条件は全方式で共通。直前出力だけの方式も、前段が保持したIDを最終回答に使える。原文再読ではプログラムがIDを照合し、対応した行だけを渡す。初見8件はほかの試験と文書を分けた。以前にコンテキスト超過が確認された16K資料の補足後1問を、既知例として別に測った。全体履歴が上限で止まった場合も記録し、全方式が完了できた問いの結果も別に集計する。[合成資料・正解と生成コード](panel.py)・[Appleのトークン計数](source-tokens.json)

## 新規8件の結果

| 方式 | 最終回答まで完了 | 値と根拠が正解 | 最大送信入力 / 生成 | 全方式が完了した短い4件の総送信入力 |
|---|---:|---:|---:|---:|
| 全履歴 | 4/8 | 2/8 | 6,110トークン | 29,201トークン |
| 直前出力 | 8/8 | 2/8 | 3,269トークン | 16,225トークン |
| 直前出力と原文再読 | 8/8 | 3/8 | 3,410トークン | 17,120トークン |

短い4件の原文は3,054〜3,230トークン。全方式が完了し、値と根拠の正答は順に2/4、1/4、2/4件だった。原文再読は全履歴と同じ正答数で、送信入力を41.4%減らした。例えば `notice-s02` では、直前メモだけでも正しい「粗目軽石」を答えたが出典の行を誤った。原文を読み戻すと、正式な行E012も返せた。

長い4件は8,465〜8,551トークン。全履歴では4件すべてが途中で入力予算を超えた。圧縮した2方式は全件で最後まで生成し、値と根拠の正答は両方式とも1/4件。全履歴の長文は途中で打ち切られるため、上表の送信量の比較には短い同一4件を使った。[全方式が完了したケースの集計](results/summary.json)

### 既知のコンテキスト超過1件

模型の銘板を問う以前の合成QAに、巡回時期を指定する補足を与えた。原文に行IDを付けた入力は18,118トークン。6段階に分けると、直前出力だけで17.60秒、原文再読付きで22.93秒で、ともに正式な「浜風」と出典L324を返した。1生成の最大送信入力はそれぞれ3,421と3,610トークンだった。この1問では履歴の分割と圧縮で正答まで回復した。単一のプロンプトだけで計数・生成上限を超える失敗に対しては、そのプロンプト自体を分割する必要がある。[以前の同一入力のエラー再現](../mode_improvements/results/retry-diagnostics)・[6段階のメモと最終回答](results/observations.json)

## 再現

```sh
python3 -B eval/handoff/test_handoff.py
python3 -B eval/handoff/handoff.py verify
python3 -B eval/handoff/handoff.py run --doctor target/release/afmcli --out ../afm-handoff-rerun
```

`verify` は保存済みの各生成から段階ごとの入力を再構成し、指紋と採点を照合する。`run` はCore Advancedが利用可能なMacで実行する。中断後は同じ出力先を指定すると、完了したケース・方式から続行する。[各段階の生出力と入力トークン](results/observations.json)・[完了・正答・送信量・時間](results/summary.json)
